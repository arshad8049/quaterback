# Task curation (QB-30)

How benchmark tasks are written, qualified and frozen. The **dev set** in this repository was written on the QB development side. The **holdout** must be written by someone outside QB development, following this guide (`docs/bench/protocol.md` §2).

## Repositories

Tasks run against public repositories pinned in `bench/repos/repos.json` and built by `bench/repos.js`. A spec names its repository as `qb-bench:<name>`, never as a path on one machine.

The base of a task repository is the pinned upstream commit plus **one** deterministic commit (fixed author, committer and date):

- `package.json`: `scripts` becomes the node:test command only. Lifecycle scripts and coverage/lint wrappers are dropped, and `devDependencies` are cut to the packages the upstream tests import.
- `package-lock.json`: the pinned lockfile from `bench/repos/<name>.package-lock.json`. The lockfile is generated by `node bench/repos.js lock <name>` and resolved **as of the upstream commit's date** (`npm install --before`), the dependency set upstream tested against. A later release of a transitive dependency broke a base's own tests once (set-cookie-parser 2.7.2 in light-my-request).
- `.quarterback.json`: the node:test command (QB-20), so visible tests can be verified.
- `remove`: the listed files are removed. One example is a test that needs a heavy toolchain (fast-json-stringify `test/webpack.test.js`); another is an `.npmrc` with `package-lock=false`.

Every other file is upstream bytes. The same pin plus the same edits give the same `base_rev` on any machine (`test/unit/qb30-repos.test.js`).

Built checkouts live outside the QB repository (`QB_BENCH_REPOS`, default `~/.qb/bench-repos/built`), so a hidden suite is never inside a task repository. The grader checks this too (`suite_leaked`).

## Writing a task

```
bench/curation/<ID>/task.json                 the task (below)
bench/curation/<ID>/reference/<files>          changed files of a known-correct implementation
bench/curation/<ID>/incorrect/<label>/<files>  ≥ 2 representative wrong implementations
bench/suites/<ID>/<files>                      the hidden suite (installed at test/hidden)
```

`task.json` contains:

- `id`, `split` (`dev` | `holdout`), `stratum` (`type`, `repository`);
- `repo` (`qb-bench:<name>`) and `base_rev` (from `node bench/repos.js build <name>`);
- `prompt`: the **only** text an agent sees;
- `requirement`: the precise behaviour, for graders and adjudicators. It is never sent to an agent;
- `oracle.acceptance_criteria`: the human-written contract the C–F arms run from (QB-13). It must not contain hidden-suite content;
- `suite.command`;
- `adjudication_rules`;
- `provenance`.

Rules the dev set follows, which the holdout author should follow too:

1. **The hidden suite tests only what the prompt determines.** When the prompt leaves a choice open (wording of a message, rounding of an edge case), either the prompt states it or the suite doesn't test it. The `requirement` spells out the full behaviour the suite checks.
2. **Prefer real behaviour.** Most dev tasks are defects or gaps that exist at the pinned commit, each confirmed by a probe before the task was written. The pinned behaviour is noted in `provenance.notes`.
3. **Incorrect implementations are plausible mistakes**, not sabotage: a partial fix (only the first argument, only one of three formats), the wrong unit (seconds vs milliseconds), a mutating shortcut, a duplicated copy left behind by a refactor. Each must fail by **tests failing** (`tests_failed`), not by a load error, so suites build inside tests, not at file load.
4. **`already_satisfied` tasks have no `reference/` tree.** The correct change is none: the empty patch must pass, and the incorrect trees are unneeded "fixes" that break working behaviour.
5. **Refactor tasks** may check structure (the new module exports the function; the old file no longer defines its own copy) as well as unchanged output.
6. Suites target Node 24 (the agent image) and the repository's own test style. They must not depend on wall-clock time, the network or the timezone.

## Qualify, approve, freeze

```
node bench/curate.js qualify <ID|all>
node bench/curate.js freeze  <ID|all> --approver "<name of a person>"
```

- **qualify:**
  - generates the reference and incorrect patches against the pinned base;
  - grades each with the **real** grader in the hardened sandbox (`--network none`, `npm ci` behind the deps proxy);
  - requires the reference to `pass` and every incorrect patch to `fail` with `tests_failed` (`bench/qualify.js`);
  - writes `bench/specs/<ID>.draft.json`: the spec with `oracle: null` plus the oracle draft. Nothing is approved or frozen.
- **freeze:**
  - a named **person** approves the drafted oracle; the tool refuses an empty approver or one that names a tool or model;
  - `spec.oracle.approved_by` records them;
  - the spec is frozen in `bench/specs.lock.json` (`bench/spec.js`; a later change needs a new version with a disclosed changelog entry) and written to `bench/specs/<ID>.json`.

For the **holdout**, the independent author keeps the holdout curation trees and suites out of QB's development history until the protocol review. The reviewer then approves the exact holdout set hash (`bench/plan.js` `holdoutGate`).

**Known limits:**

- The dev set is mostly small, one- or two-file changes in libraries with good test suites. It has one integration task and no multi-repository task.
- It is written by the QB side. It exists to debug the harness and set the trial count, never for headline claims.
